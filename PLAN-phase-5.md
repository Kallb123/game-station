# Phase 5 — polish

**Not started.** [`PLAN.md`](PLAN.md) is the source of truth for scope and phase order; §7 there
carries this phase's entry and its done-criterion, and §2, §3.7, §5.2, §6 and §8 carry the parts of
this design the rest of the app has to agree with — all five updated in the commit that added this
file, because a plan that contradicts the document it defers to is two documents nobody can trust.
What this phase learns while building it goes into `PLAN.md` §7 when the phase closes (PR 8).

The plan for the four things that turn six working screens into a shipping app: sound, haptics, an
accessibility pass, and a layout that survives rotation and a tablet.

**Three deviations from `PLAN.md` §7, decided before this plan was written:**

1. **`flutter_soloud` is out.** It resolves `http` into the shipped graph at every version — 2.1.7,
   3.5.4 and 4.1.7 all declare `http: ^1.3.0` — and `tool/check_offline.dart` fails on `http`.
   `minisound 3.0.1` replaces it: a clean graph, the same six platforms. §3.1 has the resolution
   table, and the swap is why this phase is planned before it starts rather than during it.
2. **No music beds.** §7 asks for "sound effects and light music"; the owner's instruction is no
   music on the home, menu or Sudoku screens. The arcade keeps music, generated here like every other
   sound: the four-note march of §3.4, whose tempo is the alien block's own march interval.
3. **No i18n scaffolding.** §7 asks for `.arb` files with English first. Dropped on the owner's
   instruction — no translation is planned, and an `.arb` pipeline with one locale in it is a build
   step and a lookup indirection bought against a need nobody has. §2 records what changes if a
   second language is ever wanted.

## 1. Scope and constraints

| Constraint | Rationale and mechanism |
|---|---|
| The audio dependency drags in no network package | `PLAN.md` §2 bans `http` outright and `tool/check_offline.dart` reads the resolved graph. Settled before this plan: `minisound 3.0.1` adds four packages and no `http`; `flutter_soloud`, `audioplayers`, `assets_audio_player` and `soundpool` all resolve `http`. §3.1 has the table |
| The installed APK requests no permission at all | `tool/check_apk_permissions.sh` fails on any `android.permission.*`, and `android-apk.yml` runs it on the release APK as the Android leg of CI. `minisound_ffi`'s own manifest declares `RECORD_AUDIO` for its recorder, which manifest-merges into the app — so the app's manifest removes it with `tools:node="remove"` (§3.2). A children's app that asks for the microphone is a listing liability and a broken promise; here it is a red build |
| Nothing in the app can record | The removal above is the platform half. The source half is a test asserting `lib/` never imports `package:minisound/recorder.dart` or `rec.dart`, modelled on `test/no_random_test.dart` — so reaching for the API fails before the manifest does |
| Audio failure is silence, never a crash | `AppAudio.init` catches everything and latches into a silent state (§4.2). Linux without ALSA or PulseAudio, a locked audio device, a CI machine with no sink: a child's game must play without sound, and `AGENTS.md` forbids surfacing an internal error to the player |
| No sound plays with `settings.sound` false, and no arcade music with `settings.music` false | Both are checked in `AppAudio`, not at the call sites: one place to test, and a new call site cannot forget. Widget tests assert a muted run produces an empty motif log |
| Nothing on the launch path waits for audio | `PLAN.md` §9's two-second cold start. `Player.init` and eleven `loadSoundAsset` calls happen on the first play request, not in `main` — the first tick may be late, and a late tick is cheaper than a slow launch |
| The simulation stays clock-free, RNG-free and Flutter-free | `PLAN-phase-4.md` §3, enforced by `tool/check_determinism.dart` and `test/no_random_test.dart`. `InvadersSim` gains an append-only event buffer and a `drainEvents()`; it never calls the audio layer, so `invaders_sim_equivalence_test.dart` and the 60/144 Hz guarantee are untouched |
| Every sound is generated by a committed script | `app/assets/audio/README.md` and `assets/LICENSE-ASSETS.md`: arithmetic in `tool/audio/generate_motifs.py`, no sample library, no third-party licence in the tree. `--check` re-renders and compares bytes, so a hand-edited asset fails |
| Haptics never add a permission | `HapticFeedback.selectionClick`, `.lightImpact` and `.mediumImpact` route through `View.performHapticFeedback` and need no permission; `HapticFeedback.vibrate()` needs `android.permission.VIBRATE`. A scanner test bans `vibrate(` in `lib/`, and the APK check catches it from the other side |
| Haptics only where there is a motor | `defaultTargetPlatform` in `TargetPlatform.android \|\| .iOS`, the check already at `settings_screen.dart:191`, moved to `core/haptics.dart` so three call sites share one answer rather than copying it |
| No control signals its state by colour alone | `PLAN.md` §7's accessibility rule. Selection is an `AppBorders.selected` 3 dp ring plus an icon or a label everywhere it appears; per-screen widget tests assert the ring, and `tokens.dart`'s `AppPalette` doc already commits to it |
| Every screen is usable at 200% text scale | A sweep test pumps every route at `TextScaler.linear(2.0)` and fails on any layout exception — a `RenderFlex` overflow throws in a test, so `tester.takeException()` is the assertion. `ScreenScaffold` already avoids `AppBar` for this reason |
| Every screen survives rotation | The same sweep, at three window sizes covering portrait, landscape and a tablet. Nothing in the app locks orientation today, so this is a promise the code has never been asked to keep |
| A tablet does not stretch the Sudoku grid | The board is capped and centred rather than filling a 10" screen: a 240 mm grid means a child's arm travels the width of the table for one digit. `SudokuGridView` already draws square from the shorter side; the cap is a `maxWidth` above it (§4.8) |
| Tap targets stay at their floors in every layout | `AppTapTargets.min` 56 dp and `.primary` 72 dp, already enforced through `AppTheme`. The landscape layouts re-assert them per control in tests, because a `Row` in a 320 dp-tall window is where a floor gets quietly broken |
| `tool/verify.sh` green before every commit | It is what CI runs, in the same order (`AGENTS.md`). Measured at this phase's planning: 490 app tests in 37 s. The sweep tests here pump whole screens, which is the expensive kind of test, so the phase budgets **under 60 s** for `flutter test` and states what it costs when it closes |

## 2. Non-goals

| Not doing | Why |
|---|---|
| Background music on the home, menu, profile, settings or Sudoku screens | The owner's instruction, and it agrees with the audience: a loop playing under a puzzle in a room with other people in it is the first thing a parent turns off. The arcade march is different — it is the game's clock made audible (§3.4) |
| A volume slider, or per-category volumes | Two switches, `sound` and `music`, and the device's own volume keys. A mixer is a settings screen a six-year-old can break; per-motif levels are set in the synthesiser instead (`assets/audio/README.md`) |
| `.arb` files, `flutter_localizations`, or any translation | The owner's instruction. Every string in the app is a Dart constant today, and the largely numeric UI keeps a later move cheap: the screens name their strings as public constants (`settings_screen.dart`'s `soundLabel` and friends) because the tests read them, and that is already the list a future `.arb` would be seeded from |
| Text-to-speech, or reading the board aloud | Screen readers do this. Adding a second speech path means owning pronunciation and interruption for two audiences |
| A dedicated colourblind mode | The palette is safe for everyone, or it is not fixed by a mode a parent has to find. Colour never carries state alone (§1), which is the part a mode would have bought |
| Sound for the drawing board | Phase 8 (`PLAN-phase-8.md`), whose pencil has no sound designed for it yet. `assets/audio/README.md` already says so |
| Gamepad support, `gamepads`, or rumble | `PLAN.md` §4.2 puts it after the first release. Rumble is haptics on a device the app has no other reason to know about |
| Music that reacts to Sudoku progress | The generated march works because Invaders already has a tempo. A puzzle has no beat, and inventing one means inventing a music director |
| An emulator job for `integration_test/` | `PLAN.md` §9's open question, inherited not answered. The two smoke tests stay hand-run (`AGENTS.md`), and this phase adds no third |

## 3. Approach

### 3.1 Playback: `minisound`, and why not `flutter_soloud`

`PLAN.md` §2 names `flutter_soloud` for audio. Resolving the graph before writing this plan — the same
step `PLAN.md` §10 credits for phase 8's shape — shows it cannot be taken:

| Package | Resolved version | Adds to the shipped graph | Verdict |
|---|---|---|---|
| `flutter_soloud` | 2.1.7, 3.5.4, 4.1.7 | `http`, `http_parser`, `web`, `ffi`, `logging`, `path` | **Rejected.** `http: ^1.3.0` is a direct dependency at every version, for its `loadUrl`. `tool/check_offline.dart` fails on `http` in the runtime closure, and narrowing that check is the one thing `AGENTS.md` says never to do |
| `audioplayers` | 6.8.1 | `http`, `file`, `synchronized`, `uuid`, five platform packages | **Rejected.** Same failure, plus a larger graph. `flame_audio` is rejected with it: it is a wrapper over this |
| `assets_audio_player` | 3.1.1 | `http`, `rxdart`, `uuid` | **Rejected.** Same failure |
| `soundpool` | 2.4.1 | `http` through its web implementation | **Rejected.** Same failure, and no Linux or Windows support to compensate |
| `flutter_pcm_sound` | 3.3.3 | Nothing — `flutter` alone | **Rejected.** The cleanest graph available and only Android, iOS and macOS: no Windows, no Linux. It is also a raw PCM sink, so taking it means writing a real-time mixer in Dart to feed it. Both halves are wrong for a polish phase |
| **`minisound`** | **3.0.1** | `minisound`, `minisound_ffi`, `minisound_platform_interface`, `minisound_web`, and the SDK's `flutter_web_plugins`. No `http` | **Taken.** Android, iOS, Windows, macOS, Linux and web from one package, MIT, and `miniaudio` is vendored in `minisound_ffi/src/external/miniaudio` rather than fetched at build time |

What the API gives, and what it does not:

```dart
final player = Player();                                  // package:minisound/player_flutter.dart
await player.init(32);                                     // periodMs — latency against crackle
await player.start();
final sound = await player.loadSoundAsset('assets/audio/sudoku/place.wav');
sound.volume = 0.7;                                        // per sound, 1.0 default
sound.play();                                              // stop() then resume(): one voice
sound
  ..isLooped = true
  ..loopDelay = Duration.zero;                             // the UFO warble
```

- **One voice per loaded sound.** `Sound.play()` is `stop()` then `resume()`, so a retrigger cuts the
  previous instance. For a placement tick or an alien exploding that is what should happen anyway —
  two aliens dying in the same frame are one explosion. Where it would be wrong is a long sound
  overlapping itself, and there is none in the set (§4.1's longest is the 1.4 s fanfare, and a puzzle
  is solved once).
- **No master volume and no engine-wide pause.** Ducking is therefore this app's job: `AppAudio`
  holds every loaded `Sound` and stops them on background (§4.2).
- **`pitch` exists** and changes speed with it. Not used: every motif is a separate file, so the
  README table stays the documentation instead of a multiplier in Dart deciding what a sound is.
- **Assets are read through `rootBundle.load`**, which is why `assets/audio/` finally gets declared in
  `pubspec.yaml` — the commented-out block there has been waiting for this phase.

### 3.2 `RECORD_AUDIO` has to be removed, not tolerated

`minisound_ffi/android/src/main/AndroidManifest.xml` is three lines, and one of them is
`<uses-permission android:name="android.permission.RECORD_AUDIO" />` — declared for the recorder API
this app never touches. Android's manifest merger pulls it into the app, where two things reject it:
`tool/check_apk_permissions.sh` fails on any `android.permission.*`, and a store listing for a
children's app would show microphone access.

The app's own manifest removes it:

```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:tools="http://schemas.android.com/tools">
    <!-- minisound_ffi declares RECORD_AUDIO for its recorder, which this app never uses.
         PLAN-phase-5.md §3.2: a children's app requests no microphone, and
         tool/check_apk_permissions.sh fails the build if this line stops working. -->
    <uses-permission android:name="android.permission.RECORD_AUDIO" tools:node="remove" />
```

`tools:node="remove"` is the merger's own mechanism, and the evidence is the built artifact rather
than the source: CI's `build-android` leg calls `android-apk.yml`, which runs the permission check on
the release APK. If the removal ever stops working — a dependency bump, a merger change — that job
goes red. This is the first pull request's done-criterion for exactly that reason.

iOS and macOS need nothing equivalent: playback touches no protected resource, so no
`NSMicrophoneUsageDescription` and no `com.apple.security.device.audio-input` entitlement. The macOS
sandbox entitlements stay as they are.

### 3.3 Sounds are events out of the model, not calls from the widgets

Both games already own their state in a plain-Dart model — `SudokuSession` and `InvadersSim` — and
both know things the UI above them does not: whether an `enter()` actually changed a cell, whether the
alien block stepped this frame, whether a digit was wrong on a profile that flags wrongness. So each
model emits events and the layer above plays them:

- `SudokuSession` sets a single `SudokuEvent?` slot per mutation, drained in the play screen's
  existing `_onSessionChanged` listener. A no-op `enter()` on a given emits nothing, so the tick
  cannot fire for a tap that did nothing.
- `InvadersSim.step()` appends to a bounded buffer; `InvadersGame.update` drains it after stepping.

The alternative was playing sounds from the call sites — the keypad button, the pad's FIRE listener.
It was rejected on both games for the same reason: the widget knows what was pressed, not what
happened. FIRE held against a cooldown is the clear case — the button is down for 350 ms and one shot
leaves the ship.

Neither model gains a dependency on the audio layer, which keeps the events testable with no
`Player`, no bindings and no assets: a `List<SudokuEvent>` is compared against a scripted sequence of
moves.

### 3.4 The arcade's music is the march

Invaders' music is four descending bass notes cycling as the formation steps, and the original tied
the two together in hardware: the aliens' step *is* the beat, so the music accelerates as the block
thins because the block is moving faster. This app already has that number.
`InvadersSim._currentStepInterval()` scales `rules.baseStepForWave(wave)` by the fraction of aliens
still alive, clamped to `rules.minStep` — 0.70 s down to 0.09 s on normal, 1.10 s down to 0.20 s on
easy.

So the design is: **one `alienStep` event per march step, and the audio layer plays `march_1`,
`march_2`, `march_3`, `march_4` in rotation.** Consequences worth stating:

- No tempo state anywhere. No loop to keep in sync with a simulation that pauses, restarts, drops a
  backlog of up to `maxStepsPerFrame` steps, or ends. The march stops when the block stops because the
  events stop.
- Each note must be shorter than the shortest interval it can play at, or the retrigger of §3.1 cuts
  it: 0.09 s on normal, so the notes are **70 ms**.
- Eleven notes a second at the floor is a fast pulse. Whether it reads as a drum roll or a buzz is a
  question for ears, not for this document — §9 carries it, with skipping alternate notes below
  0.12 s as the fallback if it buzzes.

The looping alternative — four bars of bass on a loop with its playback rate driven by the alive
count — needs a rate multiplier per frame, a loop that survives pause and restart, and an answer for
what happens between waves. It buys nothing: the same four notes come out.

### 3.5 Haptics: three calls, and a ban on the fourth

`HapticFeedback` is in `flutter/services.dart`, so no dependency. Only three of its methods are used —
`selectionClick`, `lightImpact`, `mediumImpact` — because they route through Android's
`View.performHapticFeedback`, which needs no permission. `HapticFeedback.vibrate()` and
`heavyImpact` reach `Vibrator`, which needs `android.permission.VIBRATE`; adding a permission to
this app costs the promise in §1. A scanner test bans the two names in `lib/`, mirroring
`test/no_random_test.dart` down to its self-tests, and the APK check catches the same mistake from
the other end of the build.

### 3.6 The load-bearing decision

**`minisound` as the playback layer.** Everything else here is additive to screens that exist: the
event plumbing, the motifs, the haptics and the layout work all stand whatever plays the bytes. If
`minisound` fails a device pass — no sound on an iPhone, a crash on a cheap Android tablet — the
fallback is not another package, because §3.1's table has no clean one left. It is an in-repo method
channel over `SoundPool` on Android and `AVAudioPlayer` on iOS with desktop silent, which is phase
8's picker problem again (`PLAN-phase-8.md` §3.3) and a phase of its own. `AppAudio` is therefore an
interface with the package behind it (§4.2), so the swap is one file — and the risk is front-loaded:
PR 1 puts it on real hardware on all three of Android, a desktop and, if a Mac is available, iOS.

## 4. Design

### 4.1 The motif set

Six Sudoku files already exist in `app/assets/audio/sudoku/`, synthesised by
`tool/audio/generate_motifs.py` (`assets/LICENSE-ASSETS.md` has their rows). This phase adds eleven
arcade files to the same script — a function each, a row each in `MOTIFS`, in the README's table and
in the licence inventory:

| File | Plays when | Level | Length |
|---|---|---|---|
| `arcade/march_1.wav` … `march_4.wav` | One per alien step, in rotation (§3.4) | −14 dBFS | 70 ms |
| `arcade/shoot.wav` | The ship fires | −16 dBFS | 90 ms |
| `arcade/alien_hit.wav` | An alien is destroyed | −12 dBFS | 180 ms |
| `arcade/ufo_loop.wav` | While the UFO is on screen, looped | −20 dBFS | 400 ms |
| `arcade/ufo_hit.wav` | The UFO is destroyed | −8 dBFS | 350 ms |
| `arcade/player_hit.wav` | The ship is destroyed | −8 dBFS | 500 ms |
| `arcade/wave_clear.wav` | The last alien of a wave dies | −8 dBFS | 700 ms |
| `arcade/extra_life.wav` | The 10,000-point bonus life | −8 dBFS | 600 ms |

The design rules are the script's existing ones (`generate_motifs.py`'s header): C major at
A4 = 440 Hz so two overlapping motifs still sound like one app, raised-cosine attacks and a 6 ms
fade so nothing clicks, and levels set per motif rather than normalised flat. Four specifics for this
set:

- **The march is four descending notes** — the sequence a child recognises as this game — rendered
  with the `MUTED` timbre a low note needs to stay a pulse rather than a hum.
- **Explosions are filtered noise, not tones.** `low_pass` over white noise: the script has the
  filter and no noise source, so one is added beside `render`.
- **`player_hit` is the loudest thing bar nothing, and still not scary.** `AGENTS.md`: no scary
  failure states. A descending noise sweep, not a klaxon.
- **No `game_over` motif.** The last `player_hit` plus the game-over card is the ending; a second
  sound on top of the card is a sound played over a screen a child is reading.

`python3 tool/audio/generate_motifs.py --check` compares bytes past the 44-byte header, so the script
and the committed files cannot drift. It stays out of `tool/verify.sh` and CI for the reason the icon
script does: the outputs are committed, and no build should need a synthesiser. **The numbers are the
sound — every added motif is listened to before it is committed.**

### 4.2 `AppAudio`: the mute-aware wrapper

`lib/core/audio/` gets three files: the motif enum, the interface with its two implementations, and
the provider.

```dart
/// Every sound in the app, and the asset each one is.
enum Motif {
  sudokuPlace('sudoku/place.wav'),
  sudokuCorrect('sudoku/correct.wav'),
  sudokuWrong('sudoku/wrong.wav'),
  sudokuErase('sudoku/erase.wav'),
  sudokuHint('sudoku/hint.wav'),
  sudokuComplete('sudoku/complete.wav'),
  arcadeMarch1('arcade/march_1.wav'),
  // … arcadeMarch2, 3, 4, arcadeShoot, arcadeAlienHit, arcadeUfoHit,
  //   arcadePlayerHit, arcadeWaveClear, arcadeExtraLife
  arcadeUfoLoop('arcade/ufo_loop.wav');

  const Motif(this.asset);
  final String asset;

  /// Whether `settings.music` gates this one rather than `settings.sound`.
  bool get isMusic => switch (this) {
    Motif.arcadeMarch1 ||
    Motif.arcadeMarch2 ||
    Motif.arcadeMarch3 ||
    Motif.arcadeMarch4 => true,
    _ => false,
  };
}

abstract interface class AppAudio {
  /// Plays [motif] once, at [gain] times its own level. Silent when the
  /// setting that gates it is off, when the engine failed, or on a platform
  /// with no audio device.
  void play(Motif motif, {double gain = 1.0});

  /// Starts [motif] looping until [stopLoop]. Only the UFO warble uses it.
  void startLoop(Motif motif);
  void stopLoop(Motif motif);

  /// Stops everything now — the app going to the background, and a quit.
  void stopAll();

  /// The settings changed: a mute takes effect immediately, mid-puzzle.
  void applySettings(AppSettings settings);
}
```

- **`MinisoundAudio`** is the real one. `Player`, lazily `init(32)`-ed and `start()`-ed on the first
  `play`, an eleven-plus-six-entry `Map<Motif, LoadedSound>` filled on demand, and a `_failed` latch.
  Every call is wrapped: any throw sets `_failed`, logs once through `debugPrint`, and every later
  call returns immediately. There is no retry — an audio device that failed at 20:00 is not worth
  asking again about on every placement.
- **`SilentAudio`** is the no-op, and it is what widget tests get by default so no test needs an
  audio device. The tests that assert *what* would play use `RecordingAudio`, a `SilentAudio` with a
  `List<Motif>` behind it (`test/core/audio/recording_audio.dart`).
- **The two settings are checked here.** `play` returns early when `motif.isMusic ? !music : !sound`,
  so a call site cannot forget, and `applySettings` stops a running loop when `music` goes false
  mid-run rather than waiting for the UFO to leave.
- **Backgrounding stops everything.** `app.dart` already holds an `AppLifecycleListener` for the save
  flush; `onPause` and `onDetach` gain `stopAll()`. The one-shots are all under a second, so what this
  really stops is the UFO warble — the sound that would otherwise still be playing when a parent
  switches to a phone call.
- **`ProviderScope` owns it**: `appAudioProvider`, overridden with `SilentAudio` in
  `test/app_harness.dart`, which is where every widget test already builds its scope.

Loading is 17 files of a few hundred kilobytes in total, `rootBundle` reads them lazily, and none of
it is on the launch path (§1).

### 4.3 Sudoku call sites

`SudokuSession` gains one nullable field and one drain:

```dart
enum SudokuEvent { placed, placedCorrect, placedWrong, noted, erased, hinted, restored, solved }

/// What the last mutation did, for the screen to turn into a sound. Cleared by
/// the read: an event is played once.
SudokuEvent? takeEvent();
```

The mapping, asserted in `sudoku_session_test.dart` against both `MistakeFeedback` values:

| Mutation | `MistakeFeedback.immediate` | `MistakeFeedback.atCompletion` |
|---|---|---|
| `enter(d)` writing a digit | `placedCorrect` / `placedWrong` | `placed` |
| `enter(d)` toggling a pencil mark | `noted` | `noted` |
| `enter(d)` that changes nothing | nothing | nothing |
| `erase()` that empties a cell | `erased` | `erased` |
| `hint()` pointing at a wrong cell | `hinted` | `hinted` |
| `hint()` revealing a cell | `hinted` | `hinted` |
| `undo()` / `redo()` | `restored` | `restored` |
| `select(i)` | nothing | nothing |
| The move that completes the grid | `solved` | `solved` |

One slot, so one sound per move, and `solved` is the move's event rather than a second one: the
trumpet replaces the placement tick on the digit that finishes the grid instead of landing 20 ms
after it.

Then `Motif` follows from the event: `placed` and `noted` play `sudokuPlace` (`noted` at
`gain: 0.7` — a pencil mark is a lighter version of the same act), `restored` plays `sudokuErase`,
and the rest map by name.

**One sound per placement, not two.** `placedCorrect` plays `correct` *instead of* `place`, where
`assets/audio/README.md` can be read as asking for both. Two motifs 150 ms apart on every digit is
mush, and their levels were set to be heard alone. The README is corrected in the same pull request —
it is the document that carries this rule, and two documents disagreeing is worse than either.

**`atCompletion` never hears `correct` or `wrong`.** That is the whole point of the mode
(`PLAN.md` §3.7): a placement sound that brightened for a right digit would hand back through the
speaker what the screen is deliberately withholding. The session decides it, because the session is
what already knows `mistakeFeedback`, and a test asserts a full wrong-digit sequence on an
`atCompletion` profile logs nothing but `sudokuPlace`.

`solved` fires the trumpet under the confetti — `PLAN.md` §3.7's "playing the sound is phase 5",
closed here. It plays whatever `reduceMotion` says: a child who asked for less movement did not ask
for less celebration.

### 4.4 Invaders events and the march

```dart
enum InvadersEvent {
  alienStep, playerShot, alienKilled, ufoAppeared, ufoLeft,
  ufoKilled, playerKilled, waveCleared, extraLife,
}

/// Everything that happened since the last drain, oldest first. Capped at
/// [maxBufferedEvents] (64) with the oldest dropped, so a sim stepped by a test
/// that never drains cannot grow without bound.
List<InvadersEvent> drainEvents();
```

Emitted from the eight methods that already detect these things — `_advanceAliens` (the step),
`_updatePlayer` (the shot), `_resolveShotsVsAliens` (the kill, the UFO kill),
`_resolveShotsVsPlayer` and `_resolveBlockVsPlayerRow` (the ship), `_checkWaveClear`,
`_advanceUfo` (arrival and departure), `_maybeAwardBonusLife`. No new state and no new branch: each
is one `_events.add` beside a mutation that is already there.

`InvadersGame.update` drains after its step loop, inside the existing `if (steps > 0)` block, and
`_march` is an `int` cycling 0–3 over `arcadeMarch1..4`. `ufoAppeared` and `ufoLeft` become
`startLoop`/`stopLoop`; `pause()` calls `stopAll()`, and `restart()` resets `_march` to 0 so every
run starts on the same note.

Determinism is unaffected: events are output only, nothing in `step()` reads them, and
`invaders_sim_equivalence_test.dart` compares simulation state. A dropped backlog
(`maxStepsPerFrame`) drops the events with it, which is right — the frames those sounds belonged to
were never drawn.

The last alien of a wave emits both `alienKilled` and `waveCleared`, and both play: two motifs 180 ms
apart, the explosion under the fanfare. Unlike a Sudoku placement (§4.3) these are two events rather
than one moment described twice, and the arcade is the loud screen.

### 4.5 Haptics

`lib/core/haptics.dart`: `AppHaptics` with the same shape as `AppAudio` — an interface, a real
implementation over `HapticFeedback`, a `SilentHaptics` for tests, a provider, and the
`settings.haptics` check inside rather than at the call sites. `_deviceCanVibrate` moves here from
`settings_screen.dart:191`, which then imports it; the settings switch keeps hiding itself on desktop
for the reason `PLAN-phase-1.md` §4.5 gives.

| Where | Call | Why that one |
|---|---|---|
| A digit or a note entered | `selectionClick` | The lightest thing available, and it fires hundreds of times a puzzle |
| A wrong digit on an `immediate` profile | `lightImpact` *instead of* `selectionClick` | The one place a child should feel a difference, and still not a punishment. One buzz per tap, the same rule as one sound per move (§4.3) |
| A pad button pressed (not released) | `selectionClick` | Confirms a press whose target is under a thumb. On release it would double every tap |
| The ship destroyed, and game over | `mediumImpact` | The two moments in a run that are worth feeling |

Nothing on a Sudoku completion: the fanfare and the confetti are the celebration, and a buzz under
them reads as an error.

### 4.6 The `music` setting, and its default

`AppSettings.music` has existed since schema v1 with no control and no consumer
(`PLAN-phase-1.md` §2). This phase gives it both: a fifth switch on the settings screen, labelled
**"Arcade music"** rather than "Music" because that is what it turns off, shown on every platform.

**Its default flips from `false` to `true`.** Invaders without the march is the game with its clock
switched off, and a child cannot ask for a sound they have never heard. What that changes and what it
does not:

- `schemaVersion` stays 1. `music` is written by every save the app has ever produced, and the default
  only applies to a file missing the key, so no migration exists to write.
- A save written before this phase keeps `music: false` until the switch is touched. Every such file
  is a development install — nothing has shipped from a store (`PLAN.md` §7, phase 6) — so the cost is
  one switch for the people testing, and the fix is discoverable on the settings screen.
- `PLAN.md` §5.2's example block shows `"music": false`, and it stays that way: the block is copied
  verbatim into a decode test, where a value that is *not* the default proves the field is read
  rather than defaulted. The flip makes that row a stronger test than it was.

### 4.7 The accessibility pass

Much of this is already done, and the plan says which so the phase does not re-derive it: `Semantics`
already wraps the controls on every screen — `grep -rln Semantics lib` names eleven files —
`ScreenScaffold` avoids `AppBar` precisely so a 200% title wraps instead of clipping,
`AppTheme` derives Material's minimums from `AppTapTargets` so a floor cannot be broken by a widget
nobody reviewed, `sudoku_cell.dart` pins its digits to `TextScaler.noScaling` and explains why, and
`reduceMotion` is or-ed into `MediaQuery.disableAnimations` in `app.dart` with `Confetti` already
returning `SizedBox.shrink()` for it.

What this phase adds:

1. **An audit, screen by screen, on a device with a screen reader** — TalkBack on Android and
   VoiceOver on iOS or macOS, walking every route in `AppRoutes`: home, profiles, settings, the
   Sudoku menu, a puzzle, the arcade menu, a run. What it looks for: a control that announces nothing,
   one that announces its state wrongly (a switch that says "Sounds" but not "on"), a decoration that
   announces at all, and a focus order that reads a screen out of the order it is drawn in.
2. **The gaps that audit finds**, as `Semantics` labels, `MergeSemantics` where a row reads as three
   things, and `ExcludeSemantics` on decoration. The HUD is the known one: `game_shell.dart` draws
   score, lives and wave as three `_HudText`s that change every frame, and a screen reader
   re-announcing them mid-run is worse than not reading them — they become one merged, `liveRegion:
   false` label.
3. **A contrast test**, not a contrast opinion: a test computing WCAG 2.1 relative luminance for
   every foreground-on-background pair `AppPalette` and the derived `ColorScheme`s produce, asserting
   4.5:1 for body text and 3:1 for large text and control borders, in both brightnesses. This is the
   one accessibility claim in `PLAN.md` §7 that nobody can check by looking, and the palette is where
   a future tweak would break it silently.
4. **A colour-alone sweep**: per-screen assertions that every selected state carries its
   `AppBorders.selected` ring or its icon — the difficulty chips, the theme choices, the mistake-mode
   choices, the pencil-mode toggle, the pad-side toggle.
5. **The text-scale sweep** of §4.8, which is the same test as the rotation sweep with a different
   axis.

### 4.8 Layout: orientation, tablets, and the sweep that guards both

Nothing in the app locks orientation — there is no `SystemChrome` call anywhere in `lib/` — so every
screen already rotates, and nothing has ever checked what happens when it does. Three of them need
work, and all of them need a guard.

`lib/core/ui/layout.dart` holds the one breakpoint, so no screen invents its own:

```dart
/// How much room a screen has, by the short side of the window.
///
/// 600 dp is Material's own compact/medium boundary and the number a "phone or
/// tablet" question actually turns on. Read from `MediaQuery.sizeOf`, not from
/// the physical device: a phone in landscape and a tablet in a split-screen
/// window are the same problem.
enum AppFormFactor { compact, expanded }

/// The widest a column of content is allowed to get: 640 dp.
///
/// A settings list stretched across a 10" tablet is a 900 dp-wide switch whose
/// label is at one end and whose control is at the other.
const double maxContentWidth = 640;

/// The widest the Sudoku board is drawn, however much room there is: 560 dp.
const double maxBoardSide = 560;
```

| Screen | Portrait | Landscape | Expanded |
|---|---|---|---|
| Home (`home_screen.dart`) | Two cards stacked, as now | The two cards side by side in a `Row` — stacked, each card is a 200 dp-tall letterbox | Cards capped at `maxContentWidth` each and centred |
| Sudoku play | Grid above, keypad below, as now | Grid left, keypad right in a `Row`: stacked in a 400 dp-tall window the board is 180 dp and a cell is 20 dp | Board capped at `maxBoardSide`, centred, keypad beside it |
| `GameShell` + `OnScreenPad` | HUD, field, pad band below, as now | The field letterboxes to 7:8 and leaves the sides empty, so the pad goes into that space — LEFT/RIGHT one side, FIRE the other, still never over the field, still swapped as a pair by `padSide` (`PLAN.md` §4.2) | Field capped so the pad stays in thumb reach rather than at the screen's edges |
| Settings, profiles | As now — both already scroll | As now | Content capped at `maxContentWidth` and centred |
| Sudoku menu, arcade menu | As now — both already use `SingleChildScrollView` | As now | Content capped at `maxContentWidth` and centred |

**The guard is one test file**, `test/layout_sweep_test.dart`, pumping every route at every
combination of three window sizes (a 360×640 phone, a 640×360 phone in landscape, an 834×1112
tablet), two text scales (1.0 and 2.0) and both brightnesses. A `RenderFlex` overflow, an unbounded
constraint or a failed assertion throws during a widget test, so the assertion is that
`tester.takeException()` is null — plus, for the Sudoku screen, that the rendered board is square and
its side is at most `maxBoardSide`. Twelve pumps per route is the expensive kind of test, which is
why §1 budgets `flutter test` and why the sweep uses one shared harness rather than one test per
combination.

**Rotation must not restart a run.** `InvadersGame` is held in `_InvadersScreenState`, so a rotation
rebuilds the widget and keeps the game — the sweep asserts the same `InvadersGame` instance and a
non-zero score survive a `MediaQuery` size change, because "the app rotates" and "the run survives
rotating" are two different claims and only the second one matters to a child.

## 7. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| `minisound` is one maintainer's package across four packages, and stops being maintained | Medium | It is reached only through `AppAudio` (§4.2), so replacing it is one file — but §3.1's table has no clean alternative left, so the real fallback is the in-repo method channel of §3.6, which is a phase of its own. Front-loaded deliberately: PR 1 puts it on hardware before anything depends on it |
| `RECORD_AUDIO` reaches the APK anyway — the merger changes, or a bump moves the manifest | High | `tools:node="remove"` plus `tool/check_apk_permissions.sh` on the built release APK in CI's `build-android` leg, which fails on any permission. The evidence is the artifact, not the source, and the check already exists |
| The vendor's own README lists iOS and macOS as untested | Medium | 3.0.0's changelog adds GitHub Actions coverage for both and claims to fix the build; CI's `build-apple` leg compiles both from PR 1, and the audit pass in PR 6 needs a VoiceOver device anyway, so playback is checked on one. If it fails there, §3.6's fallback is desktop-silent by design |
| Linux has no ALSA, PulseAudio or PipeWire and `Player.init` throws | Low | `AppAudio` catches and latches silent (§1). `PLAN.md` §8 already called Linux audio flaky and optional; miniaudio loads its backend at runtime, so a missing one is a failed init rather than a failed link |
| The march at the 0.09 s floor buzzes instead of driving | Medium | 70 ms notes so nothing is cut, and §9's open question with the fallback named: skip alternate `alienStep` events below 0.12 s, which halves the note rate and keeps the tempo readable. Decided by listening in PR 4, not by argument |
| One voice per motif swallows simultaneous events | Low | Accepted, and correct for this set: two aliens dying in one frame are one explosion, and no motif in §4.1 is long enough to overlap itself. If a later game needs two, the fix is loading a second `LoadedSound` for that motif — a voice pool in one file |
| Audio init pushes cold start past `PLAN.md` §9's two seconds | Low | Nothing audio touches `main` (§1): `init` and every `loadSoundAsset` run on the first play request. The cold-start check in §9's release checklist is what would catch a regression |
| The sweep test's 12 pumps per route make `flutter test` slow enough that people stop running it | Medium | One shared harness, `SilentAudio` and `SilentHaptics` everywhere, and a stated budget of 60 s that PR 8 reports against. If it does not fit, the brightness axis is what gets dropped — it is the one the other tests already cover |
| Rotating restarts an Invaders run | Medium | `InvadersGame` lives in the screen's `State`, so a rebuild keeps it; asserted in the sweep by checking the instance and the score survive a size change (§4.8) rather than by reasoning about widget lifecycles |
| The accessibility pass is one person's opinion on one device | Medium | Two screen readers on two platforms, and the three claims that can be mechanised are: contrast as a test, tap targets as per-control assertions, text scale as the sweep. What is left to judgement is announcement wording and focus order, and the pull request records what was checked |
| Flipping `music`'s default surprises someone whose save predates it | Low | Nothing has shipped from a store, so every affected file is a development install; the switch is on the settings screen and `schemaVersion` stays 1 (§4.6) |
| The phase grows: a mixer, a music director, a colourblind mode | Medium | §2 names each one as a non-goal with its reason, and `PLAN.md` §8's feature-creep row keeps the release line at phase 6 |
