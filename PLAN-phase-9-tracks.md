## 1. Scope and constraints

**The puzzle.** A square grid. A start port on the west edge and a goal port on the south edge. A
number beside every row and above every column. The player lays track between orthogonally adjacent
cells so that one unbroken, non-branching, non-crossing track runs from the start port to the goal
port, and each row and column contains exactly as many track cells as its number. A few cells show a
fixed piece of track from the start, so that the solution is unique. When it is solved, the traveller
makes the journey along it.

| Constraint | Rationale and mechanism |
|---|---|
| A puzzle is a pure function of its ID | `PLAN.md` §3.1–3.2, unchanged: saved progress stores IDs, not grids, so `tracks:7x7:easy:12` must be the same grid on every device in every release. The generator lives in `packages/puzzle_engine`, draws every choice from the frozen `Rng`, and is pinned by golden files exactly as Sudoku is (§4.6). `tool/check_determinism.dart` already scans all of `packages/puzzle_engine/lib`, so the new files are covered without a change to it. |
| Every puzzle has exactly one solution | A child who lays a valid track that the game calls wrong has been lied to. The generator only emits a puzzle once a solution counter that stops at 2 returns 1, and the fuzz test re-counts every generated puzzle independently (§4.4). |
| Every puzzle is solvable without guessing | `AGENTS.md`: the audience is a child. Sudoku's Expert tier exists for older players; Tracks has no tier that needs trial and error beyond one step of lookahead (§4.5). A puzzle the deduction solver cannot finish is discarded, not labelled Expert. |
| The theme never changes the puzzle | The ask is that trains can be swapped for Santa, a snail or water. If a theme could change a rule — water only flowing downhill, say — the theme would have to be part of the puzzle ID, every theme would need its own goldens, and a solved puzzle would become unsolved when a child switched skins. The engine, the session model and the save never name a theme except the one profile field that says which skin to draw; a test enforces the import boundary (§4.7). |
| Grid size is part of the difficulty choice, as in Sudoku | The ask. The menu offers a size toggle and difficulty rows exactly like `sudoku_menu_screen.dart`, and a size that cannot express a tier does not offer it — the same rule `difficultiesFor` applies to 6x6 Expert (§4.1). |
| No new package | Everything needed — the engine, `compute`, `CustomPainter`, the audio wrapper — is in the tree. `app/pubspec.yaml` and `packages/puzzle_engine/pubspec.yaml` do not change, so `tool/check_offline.dart` has no new graph to audit. |
| No binary art | Travellers and goals are palette-indexed pixel sprites declared as Dart string tables, and track pieces are drawn with `Canvas` — the approach `invaders/model/sprites.dart` and `snake/model/digits.dart` already take, extended from one bit per pixel to a small palette (§4.8). No binary in a diff, no licence line, exact at any cell size. The only new assets are four short themed sounds, synthesised by `tool/audio/generate_motifs.py` like every other sound in the app (§4.10). |
| Generation never blocks the UI thread | `PLAN.md` §3.5. Every generation goes through `compute`, behind the save's `puzzleCache`, with a pre-warm when the menu opens — the same `PuzzleSource` shape Sudoku uses (§4.9). |
| Never surface a generation failure | `AGENTS.md`. If the requested tier is not reached in 250 attempts the generator keeps the closest attempt and reports `widened`, as `generateSudoku` does. Nothing throws for a valid ID. |
| The save stays additive | `PLAN.md` §5.2. One profile field and one progress block, both optional with defaults, so `schemaVersion` stays 1 and an old save loads unchanged (§4.11). Transfer files carry the new fields with no change to `transfer_codec.dart`, because it nests the save codec's output. |
| Touch targets | Every button is at least `AppTapTargets.primary`. Grid cells are the stated exception, as Sudoku's 9x9 cells already are: at 9x9 on a 360 dp phone a cell is about 32 dp. Laying track is a drag, whose precision is the cell, not a tap target; the one tap action on a cell (marking it empty) is optional to solving (§4.12). |
| `tool/verify.sh` green before every commit | `AGENTS.md`. This phase adds goldens, a fuzz and benchmark rows to the engine suite, which is already the slow part of the run; PR 3 records the measured cost in §8 rather than assuming it is small. |

## 2. Non-goals

| Not in this phase | Why |
|---|---|
| A daily puzzle and a streak | Sudoku's daily card is its own UI and its own save fields. Tracks IDs are index-based, so a daily puzzle later is `dayIndexFor(now)` as the index and costs nothing in the engine. §9 keeps it open. |
| Rectangular grids | Square grids keep the ID to one size field and the layout to one aspect ratio. Nothing in the engine design depends on squareness beyond `TracksSpec`, so this stays cheap to add. |
| Crossings, branches, loops, several travellers | Variants of the genre that each add a rule a child must learn. One track, start to goal, is the game. |
| An Expert tier, or any puzzle that needs guessing | §1. The Sudoku engine's `Difficulty.expert` exists; Tracks refuses it the way 6x6 does. |
| Theme-specific rules | §1: the theme is a skin. Water runs through pipes exactly where a train runs on rails. |
| Ports on any edge | The start is always on the west edge and the goal on the south edge, the genre's convention. Clues then sit on the north and east margins and never collide with a port (§4.12). §3 lists the rejected alternative. |
| A tutorial screen | Minimal reading (`AGENTS.md`). The first 5x5 Easy puzzles carry many fixed pieces and teach the rule by being nearly done; whether that is enough is a device-pass question (§8). |
| Image, SVG or emoji art | §1 and §3. |
| Timed play, scores or a leaderboard | `PLAN.md` §1: no time pressure. A best time is recorded, as in Sudoku, and the timer follows `AppSettings.showTimer`. |
| Seasonal theme switching (Santa in December) | A theme is the child's choice. §9 records it as a question. |
| Any change to Sudoku's generator | Its goldens must not move; PR 3 proves it by leaving them untouched. |
| A new schema version | §4.11: every save change is an additive optional field. |

## 3. Approach

Build bottom-up, as phases 2 and 3 did: the engine first, measured, before a screen exists that could
be shaped around a guess about how hard the puzzles turn out to be.

1. **Identity and solving** — the ID, the puzzle encoding, and a solution counter that stops at 2.
2. **Generation** — the path, the clues, the fixed pieces, the deduction solver that judges the tier,
   goldens, fuzz and benchmark.
3. **The save fields**, before anything can write them.
4. **The session** — the player's board as plain Dart: laying and lifting track, marks, undo, the win
   check, mistakes and hints.
5. **The skin system** — the interface plus two deliberately different skins, train and water.
6. **The play screen**, then **the Tracks menu and the Puzzles menu** that holds it and Sudoku.
7. **Santa and the snail**, the themed sounds, then **the device pass and the close**.

**The load-bearing decision: the theme is a presentation skin over one puzzle, and nothing below the
widget layer knows which skin is drawn.** The engine, the puzzle ID, `TracksSession`, the goldens and
the solved-puzzle records are theme-free. What breaks if this changes: a theme-dependent rule puts
the theme into the ID, which multiplies the goldens by four, splits a child's solved list by skin,
and makes switching skins mid-puzzle a different puzzle. Every later decision in this file assumes
it holds.

**The second decision: the player's board is a set of connections between cells, not a piece per
cell.** Dragging a finger from one cell into the next lays exactly one connection, so the gesture and
the model are the same thing. Pieces — two straights and four corners — are derived from a cell's
connections for drawing. A piece-per-cell model would let a child place a corner that points at a
neighbour which does not point back, a half-joined state the board would then have to explain.

Alternatives considered:

| Option | Rejected because |
|---|---|
| Tap a cell to cycle through the six pieces | The standard desktop input for the genre, and the wrong one for a five-year-old: reaching a given corner takes up to six taps through pieces that do not join anything, and a 32 dp cell at 9x9 is a poor tap target for repeated taps. Dragging lays track the way a child draws a line. |
| Separate generators per theme ("water puzzles") | Contradicts the load-bearing decision; see above. |
| A per-game `generatorVersion` (`tracksGeneratorVersion`) | The save holds one `generatorVersion` and uses it for one thing: dropping `puzzleCache` when it differs (`progress_repository.dart`). Adding Tracks changes no existing ID's output — Sudoku's goldens prove it — so no bump is needed now. A later Tracks generator change bumps the shared number, which costs a Sudoku cache refill and nothing else. A second version field is a schema addition for no gain. |
| Generalising `PuzzleId` to cover both games | `PuzzleId.parse` is strict for a reason (`puzzle_id.dart`), and a union type would widen every Sudoku call site for one new game. `TracksPuzzleId` is a sibling class with its own prefix; the cache key's prefix keeps the two apart. |
| Reusing `Difficulty.expert` as a guessing tier | §1: no guessing for children. |
| PNG sprites per theme | A binary in every diff that touches art, a licence line per file, and three densities to stay sharp. The palette-string sprites are exact at any scale and reviewable as text. §9 keeps commissioned art as a later question. |
| SVG art via `flutter_svg` | A dependency graph to audit for drawings the app can make with `Canvas`. |
| Emoji travellers (🚂 🎅 🐌) | Rendered by the platform's font: different on every target, and absent on a Linux machine without a colour emoji font. A child's train should look the same on every device. |
| Ports on any two edges | More variety, but a port on the north or east edge collides with the clue numbers in that margin, and "start on the left, finish at the bottom" is a rule a child can hold. Offsets along those edges already vary per puzzle. |
| Judging difficulty by grid size alone | Size changes how long a puzzle takes, not how hard each step is. Sudoku judges by technique (`PLAN.md` §3.4); so does this (§4.5), and size is the second axis of the menu. |
| Building the skin interface with the train only, adding the others later | An interface shaped by one implementation fits that one. Water has no sprite and its "journey" is a fill rather than a moving figure, so building train and water together forces the interface to cover both shapes before anything depends on it (PR 6). |
| A fourth card on the home screen | The owner chose a Puzzles menu instead. It also keeps the home screen's three-card portrait and landscape layouts as they are, where a fourth card would have forced landscape into a 2 x 2 grid. The cost is one extra tap to reach Sudoku (§4.14). |
| A special-case "wilting" hook for the water skin alone | Every goal takes an `arrival` value instead (§4.8), so the flower reviving is one use of a shape all four skins share, not a branch the board painter has to know about. |

## 4. Design

### 4.1 Sizes and tiers

**Settled by the owner: 5x5, 7x7 and 9x9.** The goldens in PR 3 freeze them.

| Size | Offered tiers | Why this size |
|---|---|---|
| 5x5 | Easy, Medium | A first puzzle for a five-year-old: fourteen-odd track cells. **Hard is not offered**; see below. |
| 7x7 | Easy, Medium, Hard | The middle. |
| 9x9 | Easy, Medium, Hard | The largest grid whose cells match Sudoku 9x9's, which phase 3 already judged readable on a phone. Larger would mean cells under 30 dp. |

Tiers reuse the engine's `Difficulty` enum (`easy`, `medium`, `hard`); `expert` is refused by
`TracksPuzzleId.parse` and by `generateTracks`, and filtered out by the menu's `tracksDifficultiesFor`
— the same three places 6x6 Expert is refused today.

**5x5 Hard, measured in PR 3 and refused.** A 5x5 puzzle needs T3 only when almost nothing is fixed:
over 200 indices Hard was reached with 0 or 1 pieces fixed out of a path of 14, at 5 and 11 attempts
at the median; with 2 pieces fixed it took 33 attempts at the median (133 at the 95th percentile),
and with 3, 34 of 200 puzzles were widened. So a 5x5 Hard is a counting puzzle with nothing laid to
start from, which is no step up in kind from 5x5 Medium for a child, and takes two to six times the
attempts of 5x5 Medium (5 at the median). `TracksPuzzleId.parse` refuses `tracks:5x5:hard:*` and
`tracksRecipeFor` throws for it, the same refusal 6x6 Expert gets; the menu offers 5x5 Easy and Medium and a child who has outgrown
them moves to 7x7. Every other combination reaches the tier it is labelled with: no label here is
Easy by technique under a harder name, unlike Sudoku's 6x6 Medium (`PLAN.md` §3.4). What the
measurement did show is that technique alone does not separate the labels — the row and column
counts do most of the work, and even a puzzle with nothing fixed is usually Easy by technique — so
the number of fixed pieces carries the feel of a label as much as the tier does (§4.5).

### 4.2 Identity

```
id   = "tracks:7x7:medium:412"
seed = fnv1a32(id)
```

`TracksPuzzleId { TracksSpec spec; Difficulty difficulty; int index }`, with the same strict
`parse` and the same `maxPuzzleIndex` as `PuzzleId`, for the reasons `puzzle_id.dart` gives. The
prefix `tracks` is frozen once the first save holds one. `TracksSpec` holds the side length only;
`s5x5`, `s7x7` and `s9x9` are the named constants an ID can spell.

### 4.3 The puzzle

```dart
/// Connection bits for one cell. A port cell has its outward bit set.
const int north = 1, east = 2, south = 4, west = 8;

class TracksPuzzle {
  final TracksPuzzleId id;
  final int startRow;              // the start port: west edge, this row
  final int goalColumn;            // the goal port: south edge, this column
  final List<int> rowCounts;       // track cells per row, north to south
  final List<int> columnCounts;    // track cells per column, west to east
  final List<int> fixed;           // per cell, row-major: 0 or a two-bit connection mask
  final List<int> solution;        // per cell, row-major: 0 (empty) or a two-bit mask
  final Difficulty tier;           // what the deduction solver needed (§4.5)
  final bool widened;              // the tier was not reached in 250 attempts
}

TracksPuzzle generateTracks(TracksPuzzleId id);
```

A solved board has: every track cell exactly two connections; every connection reciprocated or
leaving through a port; one connected component; the port cells' outward bits set; and row and column
counts equal to the clues. That makes it a single path from start to goal — degree two everywhere
with both ends at the ports leaves no room for a branch, and one component leaves none for a separate
loop.

The encoding for the cache and the goldens is one line: size, start row, goal column, the two count
lists, then the fixed cells as `index:mask` pairs. The solution is not stored; it is regenerated, or
recovered by the solver from the clues, which is cheap and keeps the cache line short. PR 2 fixed the
format:

```
<label>|<startRow>|<goalColumn>|<rowCounts>|<columnCounts>|<fixed>
7x7|3|4|2,4,3,1,3,2,1|1,2,3,3,2,4,1|10:5,24:12
```

Decimals throughout, fixed cells in ascending index order, and an empty last field when nothing is
fixed. It holds no space, because a golden line is `index tier widened encoding` split on spaces.
`TracksClues.decode` accepts only the spelling `encode` writes, so one puzzle has one cache line.

**Built in PR 2 as two halves.** The sketch above is one class; PR 2 built only the half that has an
encoding, `TracksClues` — spec, ports, counts and fixed cells, which is everything the player sees and
everything the counter reads. `TracksPuzzle`, which wraps `TracksClues` with the ID, the solution, the
tier and `widened`, arrives with `generateTracks` in PR 3, when it is known what the generator reports;
Sudoku's `GeneratedPuzzle` grew `attempts` and `requested` the same way. The connection bits are
`TrackSide.north` and so on rather than bare top-level constants, which every importer of the engine
would otherwise have in scope.

**Built in PR 3.** `TracksPuzzle` is the second half: `id`, `clues` (a `TracksClues`, so the port
rows, counts and fixed pieces are not repeated as fields), `solution` (unmodifiable masks, row-major,
port bits included), `tier`, `attempts` and `widened`, with `requested` derived from `id.difficulty`.
The sketch's separate `rowCounts`, `fixed` and `startRow` are reached through `clues`. A fixed cell
holds the solution's full two-bit piece, the start cell's west bit and the goal cell's south bit
included. `generateTracks` is exported; `TracksStep` and `nextTracksStep` are exported for the hint
button, and `solveTracks` and `countTracksSolutions` are not.

### 4.4 The solution counter

`countTracksSolutions(clues, limit: 2)`, not exported — like `countSolutions`, it is how a puzzle is
built rather than anything the app asks. Backtracking over cells in row-major order with each cell's
state being one of seven (empty or one of six pieces), pruned at every step by:

- row and column counts: placed track never exceeds a clue, and remaining unknown cells can still
  reach it;
- connection consistency with the north and west neighbours already decided;
- no closed loop: a union-find over placed connections refuses one that joins two ends of the same
  fragment. As built in PR 2 there is no exception for the last connection: the track's two ends
  leave through the ports rather than meeting, so a valid board never closes a loop at all.

It stops at 2, and like `countSolutions` it caps its work rather than its time, returning
`unknownSolutionCount` past the cap. An optional callback receives each solution it finds, which is
how the tests check it found the right board and how a solution can be recovered from a cached line. The fuzz test calls it on every generated puzzle and asserts exactly 1, independently
of the generator's own call.

### 4.5 Generation and judging

Three stages, every choice drawn from `Rng`; nothing iterates a `Set` or `Map`. The seeds are
Sudoku's: attempt 0 is `fnv1a32(id.value)`, attempt n is `fnv1a32('${id.value}#$n')`, up to 250.
Within an attempt the frozen draw order is the ports (start row, then goal column), the walk, and one
shuffle of the path for the dig. An attempt whose walk exhausts its step budget is spent and the next seed
starts.

**Walk** (`tracks_walk.dart`). A randomised depth-first self-avoiding walk from the start cell to the
goal cell, trying directions in a fresh `Rng` shuffle at every cell entered, with a length band and a
corner-count floor per size. It prunes a branch whose length plus Manhattan distance to the goal
exceeds the band, and one that has cut the goal off from the unvisited cells. A walk that enters more
than `stepBudget` cells is abandoned. The bands below are the ones the provisional plan named,
unchanged by measurement: they hit at every size, and the generator does not need them per tier.

| Size | Path length | Corners at least | `stepBudget` | Walk hit rate |
|---|---|---|---|---|
| 5x5 | 9..15 | 3 | 1000 | 100% |
| 7x7 | 17..29 | 6 | 1000 | 99.9% |
| 9x9 | 27..45 | 9 | 1000 | 98.2% |

Hit rates are over 3000 seeds. The budget of 1000 is where more would buy a fraction of a percent
(98.7% at 3000, 99.6% at 10000 on 9x9) while a miss costs a whole walk. The turn floor exists because
an unconstrained walk often hugs an edge, which makes a dull puzzle with obvious clues. Measured on the generated puzzles, a path
runs along a whole border edge in 13 to 14% of 5x5 Easy and Medium puzzles, 3 to 9% of 7x7 and 1 to 2%
of 9x9; only 5x5 is a share worth a second look, and the lever would be the length band, not the
turn floor. It was left alone: a 5x5 path of 9 to 15 cells has little room to avoid an edge, and
those puzzles are still solved by the counts.

**Dig** (`_dig` in `tracks_generator.dart`). Start with every path cell fixed. Walk the path cells in
`Rng`-shuffled order and unfix each one if `solveTracks` at the recipe's ceiling tier still finishes
the puzzle. There is no uniqueness check per removal, unlike Sudoku's dig: the solver only reports
solved after an independent rule check, and every rule is a consequence of the game's, so a solved
report proves one solution. Stop at the recipe's fixed-piece floor once the ceiling tier has been
reached, and keep digging past the floor while it has not. The generator then runs
`countTracksSolutions` on the attempt it is about to return, as a second opinion; an attempt the
counter does not count as 1 is spent like a missed walk.

**Judge.** The deduction solver (`tracks_deduction.dart`) applies rules in tier order; the highest
tier it needs is the puzzle's difficulty. The loop runs T1 to a fixpoint, tries T2 only when T1
stalls, T3 only when T2 stalls, and returns to T1 after any progress. The rules are monotone, so the
fixpoint and the tier do not depend on the order cells are visited in.

| Tier | Deductions it may use | Label |
|---|---|---|
| T1 | A row or column whose count is met: its unknown cells are empty. One whose unknown cells exactly make up the shortfall: they are all track. A track cell with two connections takes no more; with exactly two open sides it takes both. A cell with fewer than two open sides is empty. A connection into an empty cell is impossible. | Easy |
| T2 | + No early loop: an unknown connection joining two cells of one fragment is off (the ports never meet, so there is no exception). + Reach: a cell the start cannot reach through open connections and non-empty cells is empty. | Medium |
| T3 | + One step of lookahead: assume an unknown cell track, then empty, and then each unknown side of a track cell on, then off; run T1 and T2 on a copy, and a contradiction proves the opposite. The side hypotheses are part of T3 as built. | Hard |
| — | Needs more than T3 | Discarded |

The same solver supplies hints: `nextTracksStep(clues, board)` returns the cheapest cell whose full
piece deduction proves from the clues plus the connections on the board, skipping fixed cells and
never returning an empty cell, which is what the hint button reveals (§4.13). Its precondition is a
board with no wrong connection, which PR 7 checks first.

**Recipes**, as `tracksRecipeFor` returns them. Every label's accepted tier range is exactly its own
tier. The floor is where the dig stops once the tier is reached, so the fixed count of a finished
puzzle is the floor (or one or two above it when a removal was refused); the ceiling is the most a
finished puzzle may keep before it counts as a miss.

| Size and label | Tier | Fixed pieces: floor..ceiling | Share of a median path |
|---|---|---|---|
| 5x5 Easy | Easy | 8..10 | 57% of 14 |
| 5x5 Medium | Medium | 4..6 | 29% |
| 7x7 Easy | Easy | 14..16 | 54% of 26 |
| 7x7 Medium | Medium | 7..9 | 25% of 28 |
| 7x7 Hard | Hard | 3..5 | 11% |
| 9x9 Easy | Easy | 22..24 | 56% of 39 |
| 9x9 Medium | Medium | 11..13 | 26% of 43 |
| 9x9 Hard | Hard | 5..7 | 12% |

Easy carries a little over half of its path so that the first puzzles a child meets are nearly
done (§2). Medium keeps a quarter and Hard a tenth. The fixed count is the floor in nearly every
puzzle, so Easy puzzles are the same density throughout a size; variety comes from the path and the
counts.

**Measured over 300 indices of each combination** on the development container, by a throwaway
script that is not committed (widened is 0 of 300 everywhere, and every puzzle's tier equals its
label):

| Combination | Attempts p50 / p95 / max | Fixed p50 | Path p50 | Corners p50 | Border run | Generation ms p50 / p95 / max |
|---|---|---|---|---|---|---|
| 5x5 Easy | 1 / 1 / 1 | 8 | 14 | 9 | 13% | 0.2 / 0.9 / 2.1 |
| 5x5 Medium | 5 / 19 / 44 | 4 | 14 | 9 | 14% | 0.8 / 3.4 / 10.7 |
| 7x7 Easy | 1 / 1 / 1 | 14 | 26 | 15 | 3% | 0.4 / 0.9 / 4.0 |
| 7x7 Medium | 2 / 6 / 12 | 7 | 28 | 15 | 9% | 1.0 / 3.3 / 8.0 |
| 7x7 Hard | 2 / 8 / 19 | 3 | 28 | 17 | 3% | 2.3 / 8.8 / 20.7 |
| 9x9 Easy | 1 / 1 / 2 | 22 | 39 | 23 | 2% | 0.6 / 1.4 / 4.2 |
| 9x9 Medium | 1 / 5 / 8 | 11 | 43 | 25 | 2% | 1.1 / 4.4 / 13.7 |
| 9x9 Hard | 1 / 3 / 7 | 5 | 43 | 25 | 1% | 4.2 / 18.3 / 35.5 |

"Border run" is the share of puzzles with a whole border row or column laid straight. The tiers turn
out to be cheap: the dig reaches T2 and T3 on the way down in a few attempts, because the counts give
little away once the fixed pieces are gone. So the targets below hold by a wide margin, and the
fallback this section first named, more fixed pieces in the band, was not needed.

**Targets**, unchanged from the draft and now measured: 5x5 under 10 ms, 7x7 under 50 ms,
9x9 under 200 ms at the median, with `tool/benchmark.dart` failing at three times a target as it
does for Sudoku. The benchmark's medians, 50 puzzles per combination: 5x5 Easy 0.5 ms, Medium
0.7 ms; 7x7 0.4, 0.7, 2.1 ms; 9x9 0.3, 1.0, 4.1 ms. The targets are loose by one to two orders of
magnitude, and are kept rather than tightened because the app's `compute` isolate on a low-end phone
is a different machine from this one.

### 4.6 Determinism tests

- Goldens: `test/golden/tracks_<size>_<tier>.golden`, one per offered combination (eight: 5x5 Easy
  and Medium, and 7x7 and 9x9 at all three tiers), `generatorVersion` header plus 100 lines of
  `index tier ok|widened encoding`, written by the existing `tool/regen_goldens.dart` and compared by
  `determinism_test.dart`, which fails when more than 5 in 100 of a file are widened.
- Sudoku's seven golden files are untouched by every pull request in this phase. A diff to one is a
  defect, not a regeneration. `regen_goldens.dart` rewrites all fifteen files, and Sudoku's come
  out byte-identical.
- Fuzz: `FUZZ_SEEDS` puzzles spread across the Tracks combinations as well as across Sudoku's, so
  the Tracks share is as large as Sudoku's — no crash, no non-termination, none over 2 s, exactly one
  solution each, that solution equal to the one the puzzle was built from, and the deduction solver's
  tier equal to the reported one.
- `test/rng_test.dart` and `test/hash_test.dart` already run under Chrome; nothing new needs to,
  because the Tracks code does no arithmetic wider than a cell index.

### 4.7 The session model

`TracksSession`, in `app/lib/features/tracks/model/`, pure Dart like `SudokuSession`:

```dart
class TracksSession {
  List<int> get cells;          // connection masks, row-major; fixed cells included
  Set<int>  get marked;         // cells the player marked "no track here" — never iterated for order
  bool isFixed(int cell);

  void beginStroke(int cell);   // finger down
  void strokeTo(int cell);      // finger entered an adjacent cell
  void endStroke();             // finger up; one stroke is one undo entry
  void clearCell(int cell);     // tap on a track cell: lift its connections
  void toggleMark(int cell);    // tap on an empty cell
  void undo(); void redo();     // capped at 300 entries, as Sudoku (PLAN.md §3.7)

  bool get isSolved;            // the rule check of §4.3, not a comparison with the stored solution
  int  placedInRow(int row); int placedInColumn(int column);
  Set<int> get wrongConnections; // against the solution, for immediate mistake feedback
  int  get mistakes;            // wrong connections laid, for SolvedPuzzle.mistakes
  int  get hints;
}
```

Stroke rules, each a widget-test case:

- Entering an adjacent cell connects it to the previous one, unless either already has two
  connections or the target is outside the grid other than through a port; the refusal is a soft
  bump, never an error.
- Moving back into the cell just left lifts the connection just laid, so a child can retrace a
  mistake without lifting their finger.
- A pointer that jumps more than one cell in a frame is walked cell by cell along the dominant axis,
  so a fast diagonal swipe lays an L rather than nothing.
- Fixed connections cannot be lifted.

`isSolved` checks the rules rather than equality with `solution`, and the fuzz asserts that the two
agree on every generated puzzle — uniqueness makes them the same thing, and checking rules means a
corrupt cached solution cannot refuse a correct board.

The model imports nothing from `ui/` or `skins/`. A test in the style of
`haptics_call_site_test.dart` scans `features/tracks/model` and `features/tracks/data` and fails if
either imports a skin, which is the mechanism behind §3's load-bearing decision.

**Built in PR 5, with these differences from the sketch.** (1) **Strokes are addressed by `(row,
column)`, not a cell index:** the two ports sit outside the grid — the start port is `(startRow, -1)`,
the goal port `(side, goalColumn)` — and walking a jump needs coordinates anyway. (2) **A fixed
piece's open ends are the child's to join:** the board starts as `clues.fixed` exactly, and the free
neighbour a fixed piece points into starts empty, so a fixed piece may hold a bit its neighbour does
not answer. A stroke from that neighbour into the piece lays the neighbour's half only. Seeding the
neighbour's half instead was tried first and measured: it completes cells the child never touched,
and opened 13% of 5x5 Easy, 6% of 7x7 Easy and 3% of 9x9 Easy puzzles already solved. Only the fixed
piece's own bits can never be lifted (`fixedSides`). (3) `marked` and `wrongConnections` are queries per cell — `isMarked`,
`wrongSides` (the fact) and `flaggedSides` (what the board draws, after the feedback mode) — so no
caller iterates a `Set`. (4) **Mistakes are counted when a stroke ends**, for each wrong connection the
stroke laid and left on the board: a fast swipe's overshoot that is retraced within the stroke costs
nothing. Laying a connection still plays `wrong` at once under `immediate`. (5) The cursor follows
the finger through a refusal, so the next cell entered lays from where the finger is, not from where
the refusal happened; retracing restores a mark the stroke cleared. (6) On a diagonal tie the jump
walks first along the axis of the stroke's previous step, or across columns if there was none, so a
swipe that turns a corner keeps going the way it was going. (7) **Resume refuses a board that does not
fit the puzzle** — a missing fixed connection, a port on the wrong cell, a mark on track, anything the
codec's structural check refuses — with a `FormatException`, as Sudoku's does, but **an undo stack
that does not replay into valid boards is dropped alone** and the board kept: losing history costs
less than losing a half-laid track. Undo entries are the touched cells' prior states,
`<index>.<mask>.<mark>` joined by commas (`tracks_session_codec.dart`).

### 4.8 Skins

```dart
enum TracksTheme { train, santa, snail, water }   // stored on the profile by name

abstract interface class TrackSkin {
  TracksTheme get theme;
  String get name;                 // the picker's spoken label: "Train"
  String get travellerLabel;       // Semantics: "the train"
  String get goalLabel;            // "the station"
  SkinColours colours(Brightness brightness); // ground, track, fixed track, wrong, mark, clue

  void paintGround(Canvas canvas, Rect cell, int row, int column);
  void paintPiece(Canvas canvas, Rect cell, int mask, PieceStyle style); // laid, fixed, wrong
  void paintMark(Canvas canvas, Rect cell);
  void paintStart(Canvas canvas, Rect port);     // the traveller waiting, west of the grid
  void paintGoal(Canvas canvas, Rect port, double arrival); // south of the grid; 0 waiting, 1 arrived
  void paintJourney(Canvas canvas, TrackGeometry route, double t); // 0..1 along the solved route
  Duration get arrivalDuration;    // how long the goal takes to change once the journey ends
}
```

**The goal has two states, and the arrival is a transition between them.** The water theme's flower
is wilted for as long as the puzzle is unsolved and becomes lush when the water reaches it — the
owner's design, and the moment the whole puzzle builds towards. Rather than special-case water, every
goal is painted from an `arrival` value: 0 while waiting, rising to 1 over `arrivalDuration` after the
journey ends. The other skins use it too — the station's lamp lights, the house's windows glow and
smoke rises from the chimney, the pumpkin glows — so the interface has one shape, not one for water and
one for the rest. The board's animation is then one timeline: journey `t` from 0 to 1, then `arrival`
from 0 to 1, then the fanfare and the completion card; the theme's arrival motif sounds as `arrival`
starts (§4.10). With `reduceMotion` on, both jump to 1.
A goal painted at `arrival` 1 on a board that is not solved is a bug, and a widget test asserts the
flower stays wilted on a board one connection short of solved.

`TrackGeometry` is shared: the solved path's centre line through each cell, with quarter-circle
corners, parametrised by arc length. Every skin moves at the same speed because none of them measures
the path, and the journey is testable as numbers — "at t = 0.5 the traveller is in cell 7" — without
pixels.

| Theme | Start | Goal | Track | Ground | Journey |
|---|---|---|---|---|---|
| `train` | a locomotive | a station | two rails on sleepers | grass | the locomotive runs along the route, flipped when heading west |
| `santa` | Santa | a house with a chimney | footprints in snow | snow | Santa walks the route |
| `snail` | a snail | a pumpkin | a silvery trail | soil | the snail crawls the route, slowest of the four |
| `water` | a tap | a wilted flower in a pot, lush once watered | pipes with joints | brick | water fills the pipes behind a moving front; no figure; the flower lifts and opens as `arrival` rises |

Sprites are 16 x 16 palette-indexed pixel art, one Dart string per row, one character per pixel,
`'.'` transparent, with a per-sprite palette that can differ in day and night. A goal that changes
on arrival is a short sequence of sprites — for the flower: wilted, lifting, lush — stepped through by
`arrival`, because pixel art does not tween. They are never rotated:
an upside-down Santa reads as broken. Pieces are drawn with `Canvas` paths so they tile at any cell
size. The travelling speed is the one per-skin number (the snail is slower), in cells per second, so
the snail's journey is longer but the geometry is shared.

The theme is chosen per profile — siblings on one tablet want different trains — from four picture
buttons on the Tracks menu, and the play screen reads it once per build. Switching it never touches
the session or the save beyond `Profile.tracksTheme`.

**Built in PR 6, with these differences from the sketch.** (1) **A skin is built for one
brightness** — `trackSkinFor(theme, brightness)` in `skins/track_skins.dart` — so `colours` is a
getter and every paint method agrees on which palette its sprites use; the sketch passed a
`Brightness` to `colours` alone and left the rest to guess. (2) `paintStart` takes `departed`: on a
solved board the journey draws the traveller, even at t = 0, and the start port draws what stays
behind — the train's rail stub, the water's tap. (3) `paintJourney` takes a `BoardLayout`, the
grid-to-canvas mapping both the journey and the painter use, and `cellsPerSecond` is on the
interface (train 3, water 4). (4) The timeline is plain arithmetic in `skins/journey.dart`:
`journeyFrameAt(skin, route, elapsed)` returns `t` and `arrival`, so PR 7's ticker only supplies
elapsed time. (5) **The static board painter landed here, not in PR 7**
(`ui/tracks_board_painter.dart`): the done-criterion's widget test needs a board painted by each
skin, and the rule that an unsolved board never advances `arrival` belongs to the painter rather
than to whoever drives the animation. `TracksBoardPainter.effectiveFrame` turns any frame into
`waiting` while the session is unsolved. It also draws the clues, with a tick under a met clue and
an underline under an exceeded one so that colour never carries the state alone (§4.12). Input,
the toolbar, the ticker and semantics stay PR 7's. (6) The train stops about 0.9 of a cell short of
the goal port's centre, so it never covers the station lamp that lights on arrival, and the water
is clipped to the grid so it never runs over the tap or the flower. (7) `santa` and `snail` drew
with the train skin until PR 9 built theirs. `trackSkinFor`'s switch has no default, so a fifth theme is a
compile error there rather than a silent train. (8) Piece geometry shared by the skins — a
centre line with quarter-circle corners, sampling along it, and the per-cell texture noise — is in
`skins/piece_path.dart`, so a rail, a pipe, a line of footprints and a slime trail turn identically.

### 4.9 Puzzle source

`TracksPuzzleSource` mirrors `PuzzleSource` (`sudoku/data/puzzle_source.dart`): `load` and
`prewarm`, the save's `puzzleCache` in front of `compute`, a map of in-flight loads so a pre-warm and
the tap that follows cost one generation, and one entry point that calls `generateTracks`, asserted
by a test to be the only call site in `app/lib`. Cache keys carry the `tracks:` prefix, so they
cannot collide with Sudoku's in the shared map, and the cache's existing size cap and
generator-version flush apply unchanged.

### 4.10 Sound and haptics

The existing Sudoku motifs map directly: `place` when a connection is laid, `erase` when one is
lifted, `wrong` for a refused stroke or an immediate mistake, `hint`, and `complete`. PR 9 adds one
arrival motif per theme — a whistle, sleigh bells, a soft pop, a gurgle — synthesised by
`tool/audio/generate_motifs.py` and played as the traveller reaches the goal, before the shared
fanfare. If a synthesised motif does not read as its theme on a device, that theme falls back to the
fanfare alone rather than shipping a sound that confuses. Haptics: a light tick per connection and
the completion buzz, through `core/haptics.dart` and so gated by `hapticsLevel` and the platform.

*As built in PR 9:* each skin names its motif as `TrackSkin.arrivalMotif`, so the fallback is that
getter returning null rather than a branch in the play screen. The motif plays the moment the
journey's travel ends, while the goal changes over `arrivalDuration`, and the fanfare follows when
the arrival ends. A skipped journey, `reduceMotion`, or a board whose route cannot be traced shows
the arrived goal at once, plays the motif, and holds the fanfare and the card for `arrivalDuration`,
so the two sounds never overlap and the motif never plays twice. `reduceMotion` is about movement,
not celebration, so it keeps both sounds. Both are preloaded at the moment of solving, so neither
usually pays a first-play decode on arrival; on the immediate paths the decode may still be in
flight, which the hold also covers.

### 4.11 Save fields

```json
"tracksTheme": "train",
"tracks": {
  "solved": {
    "tracks:7x7:easy:0": { "timeMs": 61000, "hints": 0, "mistakes": 1,
                           "solvedAt": "...", "clean": true }
  },
  "inProgress": {
    "tracks:9x9:hard:4": { "cells": "0a0c50…", "marks": "…", "elapsedMs": 90000,
                           "undoStack": [], "hints": 1 }
  },
  "bestTimeMs": { "7x7:easy": 61000 }
}
```

- `Profile.tracksTheme`, a `TracksTheme` with default `train`. An unknown name decodes to the
  default, so a save from a build with a fifth theme opens on an older one.
- `Profile.tracks`, a `TracksProgress`, default empty. `solved` reuses `SolvedPuzzle` — the fields
  are the same and mean the same thing. `inProgress` is a new `TracksInProgress`: `cells` is one
  hex character per cell (the connection mask), `marks` a bit string, the undo stack the session's
  compact move strings. A `cells` string that is the wrong length or not reciprocal decodes to a
  fresh board for that puzzle, never an error (`AGENTS.md`). *As built in PR 4:* the codec drops the
  entry, so the puzzle opens empty, and says nothing — the handling Sudoku's play screen already
  gives a bad Sudoku entry. The check is structural only: the key parses as a `TracksPuzzleId`;
  `cells` is that size's length in lowercase hex; no cell has more than two bits; no bit leaves
  through the north or east edge; at most one west-edge and one south-edge bit (the two ports);
  `marks` is empty or one `0`/`1` per cell. *PR 5 removed a fifth check, that every interior
  connection is reciprocated:* a fixed piece's open end is unanswered on a good board (§4.7), and
  only the session's resume knows which pieces are fixed, so reciprocity is checked there. A board that
  contradicts the generated clues passes this and is PR 5's to refuse on resume, as Sudoku's is.
- `schemaVersion` stays 1: both fields are optional with defaults, the reasoning phases 3, 4, 7 and
  8 recorded. `transfer_codec.dart` nests the save codec's output, so a players file carries both
  with no change there; PR 4 adds a transfer round-trip test that proves it rather than assuming it.

### 4.12 The play screen

```
        2  4  3  1  3        ← column clues (north margin)
     ┌──┬──┬──┬──┬──┐
     │  │  │  │  │  │ 2      ← row clues (east margin)
 🚂 →│━━│━━┓  │  │  │ 3
     │  │  │┃ │  │  │ 2
     ...
     └──┴──┴┃─┴──┴──┘
            🏠               ← goal (south margin)
   [undo] [redo] [hint]
```

- One `CustomPainter` for the board, as `SudokuGridView` is one widget: the grid plus a one-cell
  margin on each side, scaled to fit.
- A clue turns to a tick when its row or column is exactly met, and to the theme's `wrong` colour when
  it is exceeded. Both are arithmetic the child can already see, so they show in either
  `Profile.mistakeFeedback` mode.
- `MistakeFeedback.immediate` additionally draws a connection that is not in the solution in the
  `wrong` style and plays `wrong`; `atCompletion` holds that back until the track joins start to goal
  but the board is not solved.
- Undo, redo and hint are `BigButton`s below the board, within thumb reach. No mode toggle: drag lays
  track, a tap on a track cell lifts it, a tap on an empty cell marks or unmarks it.
- Auto-save on every stroke; the clock is written when it stops, as in Sudoku (`PLAN.md` §3.7).
- On solve: the journey plays (`reduceMotion` skips it to the traveller at the goal), then the theme's
  arrival motif, the fanfare, confetti and the completion card. `CompletionCard` and `Confetti` move
  from `sudoku/ui/` to `core/ui/` in PR 7 with no behaviour change if their interfaces carry nothing
  Sudoku-specific; if they do, Tracks gets its own and the reason is recorded here.

### 4.13 Hints

The hint button reveals one cell: the next cell `nextTracksStep` can prove, filled with its solution
piece and drawn as fixed. If the board holds a wrong connection, the hint points at it instead, free,
because pointing at a mistake gives nothing away — the rule Sudoku already uses (`PLAN.md` §3.7).
Hints are counted, and a hinted solve is solved but not clean.

*As built in PR 5,* the hinted piece is an ordinary laid piece — liftable and undoable — rather than
drawn as fixed: `TracksInProgress` has no field to remember which cells were hinted, so a fixed hint
would turn loose on the next launch, which is worse than never being fixed. If `nextTracksStep` finds
nothing, the hint reveals the lowest cell that differs from the solution, so the button never does
nothing on an unsolved board.

### 4.14 The Tracks menu and the Puzzles menu

The Tracks menu copies Sudoku's: a size toggle (5x5, 7x7, 9x9), a row per offered difficulty
launching the lowest unsolved index, a solved count and best time per row, and a *Keep going* card
for the in-progress puzzle with most time on its clock — the rule `SudokuMenu` uses and documents.
Above them, the theme picker. All menu arithmetic lives in a pure `TracksMenu` class tested with plain
`test()` calls, as `SudokuMenu` is.

**Sudoku and Tracks go into a Puzzles menu — the owner's choice.** The home screen keeps three
cards: the Sudoku card becomes **Puzzles**, with a puzzle-piece icon in the same palette role, and it
opens a new `PuzzlesMenuScreen` holding two large game cards, Sudoku and Tracks, built the way
`arcade_menu_screen.dart` lays out its two games. The home screen's portrait and landscape layouts do
not change shape, which is what keeps this a smaller change than a fourth home card would have been.

- Routes: `/puzzles` is new; `/sudoku` and `/sudoku/play` keep their names, so no Sudoku screen, test
  or deep link moves. `/tracks` and `/tracks/play` are new. Back from the Sudoku menu now lands on
  Puzzles rather than home — one tap further, which is the cost of grouping and the reason the
  Puzzles screen has only two cards and nothing to read.
- Sudoku's pre-warm stays where it is, on opening the Sudoku menu, and Tracks pre-warms on opening its
  own menu. Opening Puzzles warms neither: a child who taps Tracks should not have paid for a Sudoku
  generation.
- Existing tests that tap the home card by its `Sudoku` label (`app_test.dart`,
  `home_screen_test.dart`, `save_notice_test.dart`, `sudoku_menu_screen_test.dart`) and
  `integration_test/sudoku_smoke_test.dart` move to Puzzles then Sudoku in the same pull request.
- `layout_sweep_test.dart` covers `/puzzles`, `/tracks` and `/tracks/play` at 200 % text scale.
- The Puzzles menu arrives with Tracks in PR 8, not before it: a Puzzles screen holding only Sudoku
  would be a tap that offers no choice.

## 7. Risks

| Risk | Severity | Mitigation |
|---|---|---|
| A tier is rarely reached, so generation retries often and is slow | High | Measured in PR 3 before any UI depends on it; the benchmark gate fails at three times a target; a tier a size cannot express is not offered (§4.1), as 6x6 Expert is not. |
| The solution counter is slow on 9x9 with few fixed cells | High | Pruning by counts, neighbours and union-find in PR 2; the benchmark gate in PR 3; the fallback is a higher fixed-cell floor, recorded in §4.5, not a slower budget. |
| A puzzle has two solutions and a correct track is refused | High | Generator only emits count == 1; fuzz recounts every puzzle independently; `isSolved` checks rules rather than equality with the stored solution, so even a wrong stored solution cannot refuse a valid board. |
| Generated paths hug the edges and are dull | Medium | Turn-count floor in the walk (§4.5); PR 3 reports the median turn count per size in its description. |
| Drags at 32 dp cells on a small phone lay the wrong connection | Medium | Dominant-axis walking for jumps (§4.7), retracing lifts a connection, widget tests for both; on-device check in §8. |
| The skin interface fits the train and nothing else | Medium | Train and water, the two most different skins, are built together in PR 6. |
| Pixel sprites do not read as Santa or a snail at cell size | Medium | Start and goal sprites sit in the margin at full cell size, not inside a track cell; screenshots in PRs 6 and 9; checked at arm's length on a phone in §8. If one fails, its sprite is redrawn, not the format changed. |
| Children do not grasp the rule without words | Medium | The first 5x5 Easy indices are nearly complete, so the rule is shown by the board; a clue's tick shows what "met" means. No mitigation is proven until a child plays it (§8). |
| Adding Tracks moves a Sudoku golden | High | Sudoku goldens are untouched in every PR's done-criterion; CI's golden test fails on any drift. |
| `tool/verify.sh` grows past its budget | Low | PR 3 measures the added time and records it in §8; `FUZZ_SEEDS` already scales the fuzz. |
| Moving Sudoku behind Puzzles strands a child who knew where it was | Low | The Puzzles card keeps Sudoku's place, colour and size on the home screen, and the Puzzles screen holds two picture cards and nothing else. Checked with a child who already plays Sudoku in §8. |
